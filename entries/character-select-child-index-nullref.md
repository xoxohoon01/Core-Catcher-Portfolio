# 리소스 경로를 의심했는데, 범인은 자식 오브젝트 순서였다

날짜: 2026-09-28
태그: Unity, UI, 트러블슈팅

## 배경

캐릭터 선택 화면은 이름·설명·스킬 4개의 아이콘/이름/설명을 코드에서 채워 넣는 방식으로 만들어져 있었다. 그런데 이 코드가 UI 오브젝트를 이름이 아니라 **"부모 밑 몇 번째 자식인가"**로 찾고 있었다 — 예를 들어 "스킬 패널의 3번째 자식은 스킬 이름 텍스트"라는 식으로, 화면에 보이는 순서 그대로를 배열 인덱스처럼 코드에 박아둔 구조였다.

이 방식 자체는 처음 만들 때 딱히 문제가 없었다. 자식 순서가 고정돼 있는 한은 잘 작동하니까. 문제는 그 화면을 나중에 다른 작업(다른 UI 요소를 같은 계층에 배치하는 등) 때문에 다시 열어서 손보는 순간부터였다.

## 문제

캐릭터 선택 화면을 열면 `NullReferenceException`이 떴다. 스택 트레이스는 스킬 설명 텍스트를 채우는 줄 딱 한 곳을 가리키고 있었다.

가장 먼저 의심한 건 리소스 경로였다. 마침 얼마 전에 폴더 구조를 정리한 적이 있어서, "그때 캐릭터 데이터 에셋 경로가 어긋났나?" 싶었다. 그런데 확인해보니 아니었다 — 유니티에서 스크립터블 오브젝트끼리 서로 참조할 때는 파일 경로가 아니라 내부 GUID로 연결되기 때문에, 에셋을 폴더째로 옮겨도 참조 자체는 안 끊어진다. 실제로 캐릭터 데이터도, 그 안의 스킬 데이터 참조도 전부 멀쩡했다.

## 원인

문제가 난 줄 바로 앞 줄(같은 패턴으로 아이콘 이미지를 채우는 코드)은 멀쩡하게 실행됐다. 그렇다면 캐릭터 데이터도, 그 앞 자식도 문제가 없다는 뜻이었다 — 딱 그 다음 자식 하나만 이상했다.

원인은 단순했다. "3번째 자식"이라고 가정하고 짠 코드였는데, 그 사이 다른 작업을 하면서 같은 계층 어딘가에 오브젝트가 추가되거나 순서가 바뀌면서, 실제 3번째 자리에 있던 오브젝트가 텍스트 컴포넌트를 가진 오브젝트가 아니게 되어버린 것이다. 코드는 여전히 "3번째 자식에서 텍스트 컴포넌트를 가져와라"라고 시키고 있었고, 거기서 가져온 게 없으니(null) 그 다음 줄에서 바로 죽었다.

## 해결 과정

같은 패턴(자식을 순서로 찾는 코드)이 프로젝트 전체에 얼마나 퍼져 있는지부터 확인했다. 찾아보니 꽤 여러 곳에 있었는데, 위험도가 확연히 갈렸다.

- **콘텐츠가 자주 바뀌는 화면** (캐릭터 상세 정보, 스킬 트리 설명창, 카드 아이콘): 이번처럼 다른 작업 도중 계층이 흔들리기 쉬운 곳들이라 우선 정리 대상으로 삼았다.
- **레이아웃이 거의 안 바뀌는 곳** (탭 버튼, 고정된 슬롯 아이콘): 같은 패턴이긴 해도 실제로 문제가 난 적이 없어서, 굳이 지금 손댈 이유는 없다고 판단해 남겨뒀다.

정리 대상으로 고른 곳들은 "몇 번째 자식"이라는 암묵적인 규칙 대신, 인스펙터에서 직접 드래그해서 연결하는 명시적인 필드로 바꿨다. 스폰될 때마다 새로 생기는 오브젝트(예: 몬스터 머리 위 체력바)처럼 애초에 인스펙터로 미리 연결해둘 수 없는 경우는, 그 프리팹 자신에게 참조를 들고 있는 작은 컴포넌트를 하나 추가해서 같은 문제를 피했다.

## 결과 / 배운 점

- 캐릭터 선택 화면, 스킬 트리, 몬스터 체력바 전부 정상 동작을 확인했다.
- **"몇 번째 자식"으로 UI를 찾는 코드는 언젠가 반드시 깨진다.** 문제는 깨지는 시점이 그 코드를 마지막으로 만진 사람과 전혀 상관없는 작업 중일 수도 있다는 것 — 이번에도 원인은 캐릭터 선택 화면 자체가 아니라 같은 계층에 있던 다른 UI 작업이었다.
- 같은 증상이라도 원인 후보를 성급하게 하나로 좁히면 엉뚱한 곳을 계속 파게 된다. "경로가 문제일 것"이라는 첫 가설을 실제로 검증(GUID 참조 확인, 리소스 경로 확인)하고 나서야 진짜 원인 쪽으로 넘어갈 수 있었다.
- 같은 패턴이 여러 곳에 있다고 전부 다 고칠 필요는 없었다. "얼마나 자주 바뀌는 계층인가"를 기준으로 위험한 곳만 먼저 정리하는 쪽이 더 실용적이었다.
